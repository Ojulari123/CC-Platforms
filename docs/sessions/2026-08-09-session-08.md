# Session 08: Weeks 1–5 audit, Pulse frontend, shared UI layer, and the day the containers lied

**Date:** 2026-08-08 (late) → 2026-08-09
**Where it ended:** An audit against the internship plan found **Week 5 incomplete**: Forge
had no signup, no real dashboard, no learning paths, no canvas and no first-run onboarding,
and **Pulse had no frontend at all**. All of that now exists, with the auth code hoisted into
`packages/ui` as a Nuxt layer both products `extends`. A `docker-compose` YAML folding bug
turned out to have disabled `--reload` on all three services, so the stack had been serving
**stale code for a day**; everything below was re-checked after that was fixed. **Week 3 is
met; Week 4 is met except its notification clause, which is blocked at the email provider,
not in our code; Week 5's Forge work is now complete. Signup is still open to any domain.**
Nothing this session is committed.

## What was built

### `packages/ui`: the shared frontend layer
- Session 07 deliberately kept Forge's auth composable in-app ("extracts to `packages/ui`
  when Pulse gets a frontend"). Pulse got a frontend, so it extracted. `packages/ui` is a
  **Nuxt layer**, not a component library: `composables/` (`useAuth`, `useApiClient`,
  `useTokenStorage`, `usePasswordRules`), `middleware/`, `types/`, and whole **pages**:
  `pages/forgot-password.vue`, `pages/reset-password.vue`, `pages/invites/accept.vue`.
- Both frontends carry `extends: ["../../../packages/ui"]`
  (`services/pulse/frontend/nuxt.config.ts:4`, `services/forge/frontend/nuxt.config.ts:4`),
  so the login/refresh/guard path and the three emailed-link landing pages exist **once**.
  That closes the long-standing "the invite link has nowhere to land" item; identity has
  been emailing links to pages that did not exist since session 03.

### Pulse: the frontend it never had (`services/pulse/frontend/`)
- Nuxt 3 + TS + Tailwind + TanStack Query, same shape as Forge's. `pages/login.vue`,
  `pages/index.vue` (the activity dashboard: counts plus recent commits/PRs/reviews/issues,
  with a "whose activity" selector that drives `/activity/me` vs `/activity/{user_id}`),
  `pages/reports/index.vue`, `pages/reports/[id].vue` (draft → edit → submit, plus the PDF
  link), and `pages/review.vue` (the approver's queue, hanging off the `review-queue`
  endpoint built back in session 05 with no UI on it).
- The notification email's `{FRONTEND_URL}/reports/{id}` link now lands somewhere real.

### Forge: the rest of Week 5 (`services/forge/frontend/`)
- **`pages/signup.vue`**: the front door for identity's `POST /auth/signup`.
- **`pages/index.vue`**: a real dashboard, not a redirect. Backed by a new
  `/datasets/summary` endpoint returning counts + recent rows in **one** call; the paginated
  list can't answer it, because its `total` blends owned datasets and samples. It carries the
  **first-run state**: a new account has the seeded samples and nothing of its own, and the
  page says so instead of rendering an empty table.
- **`pages/learning/index.vue` + `pages/learning/[slug].vue`**, content in
  `constants/learningPaths.ts`.
- **`pages/canvas.vue`**: the Week-6 workflow builder sketched, not implemented.

### Identity
- **Name resolution via `POST /internal/users/profiles`**, behind its **own** scope
  `users:read:profile` (`app/routes/internal.py:12,25`). Split from `users:read:email` on
  purpose: a service that only draws names can't harvest the email list. Returns
  `unknown_user_ids` so the answer is total, and resolves deactivated users **flagged**
  rather than omitting them.
- **`POST /internal/users/token-versions`** under scope `tokens:verify`
  (`app/routes/internal.py:13,45`), the missing half of cross-service revocation.
- **Hard delete for never-onboarded accounts**: `platform_service.delete_user`
  (`app/services/platform.py:76`). Only for an account created by mistake; every guard errs
  towards refusing (self, platform admin, any membership, any team led or department headed).
  The evidence that an account *was* onboarded is a new explicit **`users.onboarded_at`**
  (migration `0010`), because `remove_member` deletes the membership row, so a live count
  can't see an ex-member. `email_verified` and a past accepted invite stay as backstops.
  Migration `0009` drops the dead `membership.is_active` column.
- **Phased signing-key rotation.** `keys.py` publishes the active key plus every `.pem` in
  `JWT_RETIRED_PUBLIC_KEYS_DIR` at `/.well-known/jwks.json`, so tokens signed by either key
  verify during an overlap window; retired keys verify but never sign.
  `validate_retired_public_keys()` runs at startup and **refuses the boot** on an unusable
  retired `.pem` rather than 500ing JWKS later, because that endpoint failing would break token
  verification across every service at once. Runbook:
  `docs/runbook-identity-key-rotation.md`; helper `scripts/rotate-identity-keys.sh`.
- **`forge` service client** seeded alongside `pulse`, with a deliberately smaller scope set:
  `PULSE_SCOPES = "users:read:email users:read:profile tokens:verify"` vs
  `FORGE_SCOPES = "tokens:verify"` (`app/services/service_clients.py:13,15`).

### Pulse
- **Names on everything.** `app/services/people.py` (`attach_names`) does one batched
  `/internal/users/profiles` call per response; wired into report responses, the repository
  list/detail, activity, and the PDF. Names are decoration: an id that won't resolve stays
  null rather than failing the request.
- **Dead code finished or dropped.** `reports.prompt_version` is now actually written
  (`app/services/generation.py:166,179`, migration `0006`); the never-populated commit
  line-count columns are gone (migration `0005`).
- **The GitHub OAuth callback returns you to the app.** It used to end on a JSON body in a
  browser tab; `_back_to_pulse` (`app/routes/github.py:39`) redirects to
  `{FRONTEND_URL}/?github={outcome}` with the destination pinned to config so it can't be
  turned into an open redirect.
- **Departed-user credential cleanup**: `app/services/leavers.py`. Identity can't push
  deactivations at Pulse (that coupling is what the architecture rules forbid), so Pulse asks:
  the profile answer it already fetches carries `is_active`, and a hard-deleted user comes
  back in `unknown_user_ids`. Both count as departed and the stored GitHub credential is
  dropped. Commits/PRs/reviews/issues stay: attribution is history, not a live permission.
  The failure mode the module is written around: never read "identity didn't answer" as
  "everyone left", so a chunk identity failed to answer deletes nothing.

## What was fixed

- **Revocation now actually reaches Pulse and Forge.** `crescent_core.RevocationChecker`
  asks identity's token-version endpoint and caches per user for `TOKEN_VERSION_TTL_SECONDS`
  (**60**, `services/pulse/app/config.py:27`, `services/forge/app/config.py:24`), wired into
  the single `current_user` dependency every authenticated route uses so it can't be opted
  out of. `STALE`/`UNKNOWN` → 401; `UNAVAILABLE` is **accepted on purpose** with rate-limited
  warnings, so an identity blip isn't a platform-wide outage. Window: ~15 min → ~1 min.
- **Three authorization holes in Pulse.**
  1. *Anyone's activity, anywhere.* The old `can_view` returned true for any repo lead,
     deputy or department admin, and then the query was unscoped, so it returned the target's
     activity across **every** repo, including ones the viewer has nothing to do with. Now
     `visible_repo_ids` intersects the caller's oversight with the repos the target actually
     worked in, and that list narrows the counts as well as the rows
     (`app/services/activity.py`).
  2. *Self-approval.* `_can_approve` admitted a platform admin (or a lead who authored a
     report on their own repo) before ever checking authorship. Authorship is now checked
     **first**, `decide_report` refuses with an explanation of who to ask instead, and your
     own report no longer appears in your review queue (`app/services/reports.py:47,160,208`).
  3. *Every repo visible to every signed-in user.* `list_repositories`/`get_repository` had
     no caller scoping at all: name, owner, private flag and lead/deputy ids for the lot.
     Both are scoped now, and an unrelated repo answers **404, not 403**: the existence of a
     private repo is itself worth not leaking (`app/routes/repositories.py`).
- **Rate limits key per user, not per IP.** Each service's `rate_limit.py` gained
  `user_or_address_key`, which reads the `Authorization` header and **fully verifies** the
  token (decoding it would let anyone forge someone else's bucket), counting per `user:<id>`
  and falling back to the address, never to a shared key. Routes with no caller to attribute
  a request to stay address-keyed on purpose (register/signup/login/refresh/reset,
  `/oauth/token`, the GitHub OAuth callback).
- **A proxy setting that inverted its own purpose at zero.** `TRUSTED_PROXY_COUNT` picks the
  hop counted from the right of `X-Forwarded-For`; at `0` the arithmetic selected the
  *client-supplied* end of the header, precisely the spoofable value the setting exists to
  avoid. All three configs now reject anything below 1 at load time with an explanatory
  message (`MIN_TRUSTED_PROXY_COUNT`, each `app/config.py`).
- **A JWKS amplification vector.** `JWKSClient` refreshed on any unknown `kid`, and auth runs
  *before* the rate limiter, so unauthenticated requests carrying made-up kids could drive
  one identity fetch per request. Refresh is now floored by `min_refresh_interval_seconds`
  (30s) however many unknown kids arrive, with the HTTP call outside the lock so real
  verifications don't queue behind it (`packages/core/crescent_core/jwks.py:6-45`).
- **The PDF silently deleted text.** Report bodies go into reportlab `Paragraph`s, which
  parse a small XML dialect, so any `&` or `<` an engineer typed was swallowed or blew up
  the render. Everything user- or identity-supplied is now `escape()`d before it becomes
  markup, with newlines re-added as `<br/>` afterwards (`app/services/pdf.py:3,52,80,91`).
- **Two identity write paths that never checked the department exists.** A platform admin
  passes the `dept_id` authorization guard without a membership lookup, so nothing upstream
  had proved the department was real; `create_invite` and `add_member` both went on to build
  a row against it. Both 404 now, `add_member` also rejects a team that belongs to a
  different department, and a duplicate membership race returns 409 instead of 500
  (`app/services/invites.py:22`, `app/services/departments.py:85`).
- **Test suites reading real credentials.** Pulse's `conftest.py` now pins **every** setting
  `app/config.py` declares (assigned, not `setdefault`) and blocks outbound HTTP by
  replacing httpx's transports, recording attempts in `BLOCKED_REQUESTS` so the
  error-swallowing notify path can still be asserted on. Identity's generates a throwaway
  RSA keypair in a temp dir rather than touching `services/identity/keys/`.
- **Also:** presenting a revoked refresh token now bumps `token_version` as well as killing
  the family, so the stolen *access* token dies with it; previously family revocation only
  stopped new pairs (`app/services/auth.py`). Repos gained explicit
  `PUT`/`DELETE /github/repositories/{id}/tracked`.

## Environment defects, worth writing down, because they will recur

- **`docker compose` served stale code for a day.** All three services used a folded scalar
  (`command: >`) with the uvicorn flags on a more-indented continuation line. YAML `>` does
  **not** fold a more-indented line, so the newline survived, `sh -c` read the flags as a
  second command, and **uvicorn ran with no reloader at all**. Every service is now exec-form
  on one line (`docker-compose.yml:58,98,174`) with the trap written in a comment above each.
  This is the defect that matters most below: a chunk of the day's "verification" was
  verifying a container image from the previous morning.
- **Name resolution had never once worked in the running stack.** The `pulse` service
  credential that authorises `/internal/users/profiles` was never set in the environment the
  containers read, so every name lookup failed and fell back to null, silently, because
  names are deliberately best-effort decoration. It resolved on the first try once the
  credential was actually present. Best-effort degradation and a missing credential look
  identical from the outside; that's the lesson.
- **CORS admitted one frontend origin.** Two products means two dev ports. Identity and Pulse
  now default to `http://localhost:3000,http://localhost:3001`; Forge's default is still the
  single `http://localhost:3000` (`services/forge/app/config.py:28`), fine while nothing
  calls Forge from the Pulse origin, but it will bite the same way.
- **iCloud.** The project lives in an iCloud-synced folder. Two symptoms: the venv's `.pth`
  files got macOS-hidden at one point, which makes a bare `pytest` fail to import
  `crescent_core` while `PYTHONPATH=packages/core pytest` works, a confusing split; and
  iCloud writes conflicted copies as `<name> 2`, which nothing in `.gitignore` matched.
  Rules added (`.gitignore:27-29`). **Neither symptom reproduces as of the end of this
  session** (a bare `pytest` in `services/pulse` passes and no duplicate files exist), so
  the `.pth` half in particular should be treated as "seen once, cause not fully pinned
  down", not as diagnosed and closed.

## Decisions

- **`packages/ui` is a Nuxt layer, not a component library.** It holds behaviour that must
  not fork (token storage, refresh-on-401, the route guard) plus the pages identity emails
  links to. Products keep their own look. This is what makes moving tokens to httpOnly
  cookies a one-file change later.
- **Name resolution gets its own scope, below email.** `users:read:profile` exists so a
  service that draws names never needs the scope that lists addresses. `tokens:verify` is
  separate again: every verifying service needs it, none of them should need the other two.
- **Deletion is for accounts that were never used; deactivation is for leavers.** Identity
  can't ask Pulse whether a person authored anything, so `delete_user` refuses on any
  evidence of a real working life and points at deactivation instead. `onboarded_at` exists
  because the obvious signal (a membership row) is destroyed by `remove_member`.
- **`UNAVAILABLE` from the revocation check is accepted, not a 401.** Identity being briefly
  unreachable must not log everyone out of every product. The trade is that the revocation
  window widens during an identity outage, chosen over turning one service's blip into a
  platform outage.
- **404 rather than 403 for a repo you have no relationship to.** 403 confirms the repo
  exists.
- **Pulse's department reach is derived from repos, not people.** Pulse deliberately does not
  know which department a user belongs to, so a department admin's reach over a *person* is
  computed from the only departmental fact Pulse holds: which department a repo is filed
  under. Reads as "you can see what this engineer did in your department's repos", the
  tightest rule the available data supports.

  `services/pulse/celerybeat-schedule` holds `daily-github-sync`, `crontab 0 2 * * *`,
  `last_run_at 2026-08-09 02:04:06 UTC`, `total_run_count 5`. That entry was re-read
  independently while writing this log; the commit diff was not (it needs a GitHub token and
  the running stack).
- **Week 4: PARTIALLY MET.** Generate → edit → submit → approve → PDF all work end to end,
  and the email **does** now send for real rather than logging intent. The clause is
  unmet only at the last hop: the test recipient is blocklisted at Brevo because
  `@cyphercrescent.com` addresses hard-bounce, and **the real domain is `.org`**. Brevo returns
  *success* for a send to a blocklisted address, so the failure is invisible in our logs.
  This is a provider/address problem, not a code problem, but Week 4's "the reviewer gets
  notified" bar is **not** demonstrably met until it's sent to a real `.org` address.
- **Important caveat on all of the above:** most of this only became meaningful after the
  `--reload` bug was found. Anything checked against the stack before that point was checked
  against a stale image and was re-run afterwards.

## Known limitations

- **Signup is still open to any domain.** `SIGNUP_ALLOWED_DOMAINS` defaults to `""` = allow
  all (`services/identity/app/config.py:34`) and `services/identity/.env.example:68` ships it
  blank; the README's example still names `cyphercrescent.com`, which is the domain that
  hard-bounces; the org's real domain is `.org`. **Checked at the end of this session and
  still open;** another agent may be locking it as this is written, so re-read the config
  before trusting either state. This is the single loudest pre-deploy item: an open signup on
  a service that mints tokens for both products.
- **Pulse's frontend is not in CI.** There are `forge-frontend`, `forge` and
  `forge-migrations` jobs but no `pulse-frontend`, so Pulse's new Nuxt app is neither built nor
  typechecked by CI, so it can break on `main` without anything going red.
- **The iCloud `.gitignore` rules are narrower than they look.** `* [0-9]` and `* [0-9][0-9]`
  match names *ending* in a digit (`.nuxt 2`, `dist 2`). A duplicated file with an extension
  (`index 2.vue`) still isn't matched.
- **Email verification for self-signups still doesn't exist.** `POST /auth/signup` sets
  `email_verified=False` and nothing lifts it. That flag is now load-bearing in a second
  place: `delete_user` reads it as evidence of onboarding.
- **Tokens still live in `localStorage`** on both frontends. Now a genuinely one-file change
  (`packages/ui/composables/useTokenStorage.ts`), still deferred because the correct cookie
  config depends on a deployment topology nobody has chosen.
- **Identity's single `FRONTEND_URL`** feeds both the invite and reset links, so every
  emailed link points at whichever product that variable names, worse now that there are two
  frontends and both can serve the landing pages.
- **The full stack was never driven through a browser end to end this session.** Individual
  flows were exercised; a recorded click-through of login → dashboard → report → approve, and
  the equivalent for Forge, is still outstanding.
- **`services/pulse/celerybeat-schedule` is still tracked**, and running the Pulse suite
  touches it, so it turns up as a modified binary in `git status`. It needs
  `git rm --cached` in a commit of its own; `.gitignore` alone does nothing to a tracked file.
