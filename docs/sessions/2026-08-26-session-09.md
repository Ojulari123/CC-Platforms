# Session 09: journals, the assistant, who a report is about, whose money pays for it, and getting ready to deploy

**Date:** 2026-08-09 → 2026-08-26
**Where it ended:** Pulse grew most of a product in this window. Repositories have
journals with AI rollups; an assistant answers questions out of an indexed repository and
cites the files it read; reports separate who wrote them from who they are about, which is
what made custom multi-person reports possible; personas control tone; customers can
install their own API key and set daily token allowances at three levels. The shared UI
layer gained a light theme and a rebuilt contrast ramp. `scripts/dev.sh` exists because
the front ends bake their build into an image and a plain `docker compose up` serves stale
code. Deployment is prepared and documented but not executed: nothing is live, and Forge is
deliberately not going.

Three defects were closed at the end of the window (commit dates, pull request closure
dates, and an empty conversation left behind by a refused first question), and one piece of
invention was removed: next week's goals used to be guessed from this week's commits.
Nothing in this window is committed.

## What was built

### Repo journals, and one AI readout over them

- `repo_journals` is free text a repo's members leave for each other, with the usual
  ownership rule: anyone who can read the repo can read the journal, only the author edits
  or deletes their own entry (`services/pulse/app/services/journals.py:58,69`).
- A rollup is one AI summary over the most recent entries, stored rather than computed on
  view (`journals.py:95`). It records the window it read (`covers_from`/`covers_to`,
  migration `0007_repo_journals.py`) so a rollup stays readable beside a feed that has
  moved on since.
- `_recent_entries` takes newest-first out of the database so the cap keeps the newest, then
  reverses, because a progress readout only makes sense in the order it happened
  (`journals.py:77`).
- The same migration added `llm_usage.kind`. Without it, a rollup's spend is a row with no
  `report_id` and no surface to attribute it to.

### The assistant

- **Indexing.** A repository's files are fetched, filtered, chunked with overlap and
  embedded (`app/services/repo_index.py:86,99`, `app/services/embeddings.py:76`). Chunks
  live in `repo_chunks.embedding` as a pgvector column (migration `0008_repo_index.py`).
  `indexed_repos.repo_id` is nullable on purpose: a public repository can be indexed on
  request without Pulse tracking it, so such a row has a `full_name` and no parent.
- **Resumable ingest.** `indexed_repos.ingest_sha` is a checkpoint. Chunks are written in
  batches, so a run that dies after two thousand files has two thousand files of rows
  already stored, and this column is what tells a retry those rows belong to the commit it
  is resuming (migration `0013_indexed_repo_ingest_sha.py`).
- **Answering.** The question is committed on its own before the model is called, so a
  provider outage costs the answer and not what the person typed; the answer, its citations
  and the ledger row then land in one commit (`app/services/chat.py:1-8`).
- **Citations are checked.** Every citation must equal a chunk that was really retrieved and
  really put in front of the model, and a file the answer names that was never retrieved
  produces no citation at all (`chat.py:181-203`). Citations are then narrowed to the files
  the answer actually names, because a short answer arriving with twelve sources is more
  than anyone checks.
- **Citations outlive the index.** `chat_citations.indexed_repo_id` is nullable with
  `ON DELETE SET NULL`, next to a denormalised copy of the repo name, path and snippet. An
  index is a cache that gets deleted and rebuilt; cascading from it would delete the
  evidence under answers people have already read (migration `0009_chat_conversations.py`).

### Reports: who wrote it is not who it is about

- `reports.author_user_id` had meant both since the table existed, because on a weekly
  report they are the same person. `subject_user_id` split off, and a report covering
  several people gets a `report_subjects` row each, with its own attributed section rather
  than one blended narrative (migration `0010_report_subjects.py`).
- Two columns lost NOT NULL in the same move (`repo_id`, `week_start`), which gutted
  `uq_report_author_repo_week`, because NULLs never collide. It is replaced by a partial
  unique index over the same three columns restricted to `kind = 'weekly'`, declared on the
  model too so autogenerate does not read the real index as drift.
- That migration's `downgrade()` deletes data and says so at the top of the file. Restoring
  NOT NULL is impossible while an ad-hoc report exists.

### Custom reports, in two modes

`app/services/adhoc.py` is one service path over two data sources. Mode A reads the local
tables for a tracked repository and makes no GitHub call (`adhoc.py:133`). Mode B fetches
live from GitHub for any repository, tracked or not (`adhoc.py:183`).

The permission gate on Mode B is GitHub's own, not one Pulse invented: a private repository
is readable only if the caller's own stored OAuth token can read it, so Pulse can never be
used to read a repository the person asking could not have opened themselves
(`adhoc.py:9-18`). Each subject's section is generated from a payload containing only their
records, so two people's work cannot be blended or swapped: the model writing one section
has never seen the other person's data.

### Personas

Four independent dials (length, audience, technical depth, formality) plus freeform
guidance, rather than one opaque preset string, because the useful combinations are ones
nobody would have thought to name (migration `0011_personas_and_credentials.py`). A row with
`owner_user_id` NULL is a system preset, visible to everyone and editable by no one; three
are seeded and Concise is the fallback (`app/services/personas.py:118,131`).

`reports.persona_id` is deliberately not a foreign key. A persona is a tone a user can
delete at any time and a report is a record of work that has to outlive it: a cascade would
delete reports, and SET NULL would erase the only trace of how a report was written
(migration `0012_report_persona.py`).

### Bring your own key

`api_credentials` holds a customer's LLM key, Fernet-encrypted with the same mechanism
already protecting GitHub tokens, with only `last_four` ever readable. Resolution is user,
then department, then the platform environment key, and scope beats provider preference: a
user who installed their own key pays with it even when the platform prefers the other
provider (`app/services/credentials.py:92-128`).

`bypass_token_cap` lives on the row rather than in configuration, because it may only ever
lift a cap on spend the row's owner is paying for. The platform's env key has no row, and
its `bypass_token_cap` is hardcoded False rather than read from anywhere
(`credentials.py:118-127`).

### Token allowances at three levels

`token_budgets` makes the daily cap overridable at the same levels a key already is: a user
row beats a department row beats a platform row beats `LLM_DAILY_TOKEN_CAP_PER_USER`
(migration `0014_token_budgets.py`, `credentials.py:267`). Its own table rather than a
column on `api_credentials`, because somebody spending the platform's key has no credential
row and still has to be able to lower their own allowance.

The check runs before the call, not after. `check_budget` takes what the call is about to
cost and refuses on either of two conditions: the allowance is already gone, or this call
would take it past the line (`app/services/llm_budget.py:169-193`). The estimator is a
measured approximation with its calibration written into the file, including the table of
safety factors that was walked down and where it stopped (`llm_budget.py:28-66`).

### Light and dark, and the contrast repair

`packages/ui/assets/css/tokens.css` carries two themes selected by `data-theme` on `<html>`,
with an inline boot script setting the attribute before first paint so a light user never
sees the dark default. `useTheme` keeps the choice in a cookie scoped to a shared domain, so
the theme follows a person from Pulse to Identity (`packages/ui/composables/useTheme.ts:25`).

The dark theme was rebuilt rather than tweaked. The page sat at oklch L 0.164 with the whole
five-step surface ramp packed into a 1.00 to 1.29 contrast band, so a card, a hovered row
and a selected row were within four per cent of each other and of the page: the depth system
carried no information, which was the real complaint behind "too dark to see". The page is
now L 0.205 and the ramp runs 1.00 to 1.52 with every adjacent step at least 1.08
(`tokens.css:24-37`). Lifting the page costs contrast on every ink and status token, so the
rest of the file was retuned around it.

The three rule weights are split by job. `--line-subtle` is decoration and drew at 1.06:1 on
a selected row, which is to say it did not draw at all on the surface where a rule matters
most; it now runs 2.51 down to 1.65 across the five surfaces, and 1.65 is documented as a
cell that must not be drawn rather than one that is fine (`tokens.css:38-64`). `--line` and
`--line-strong` are structural and clear 3:1 against every surface a control can land on,
not just against the page.

The contract is asserted, not written down and hoped for: `packages/ui/test/tokens.spec.ts`
computes the ratios from the stylesheet, and `tokenUsage.spec.ts` checks that nothing
interactive uses the decorative weight.

### The rest

- **Settings** (`services/pulse/frontend/pages/settings.vue`): persona and API key on one
  screen, as tabs rather than stacked sections, because neither half can be derived from the
  other.
- **Submit for approval** (`app/services/reports.py:177`): author only, editable statuses
  only, and an empty report is refused with a 422 rather than sent to a reviewer. The
  notification is sent after the commit and swallows its own errors, so a mail problem can
  never roll back a submission.
- **`scripts/dev.sh`**: the back ends mount their source and reload, the three Nuxt apps
  bake a production build into their image with no mount, so a plain `docker compose up`
  serves stale front-end code. Builds run one service at a time on purpose: building the
  Nuxt apps in parallel exhausts the Docker VM's memory and kills the daemon
  (`scripts/dev.sh:5-16`).
- **Deployment preparation**: `DEPLOY.md` is a runbook with a "what has been verified and
  what has not" section at the top, `docs/deploy-env-matrix.md` is the variable reference,
  and `render.yaml` plus the two `vercel.json` files carry the config. Forge is not deployed:
  its own pages say it is not built yet, so it is not worth an instance.

## What was fixed at the end of the window

- **Commit dates were the wrong dates in the live report path.** `committed_at` is the
  committer date, which is when a commit entered the branch, and the sync has stored that
  since week 3. The live path still read `commit.author.date` in two places: the range
  filter and the payload. A rebased or cherry-picked commit therefore landed in the wrong
  week, and the same repository was dated one way when tracked and another way when read
  live. Both now call one helper, `sync.commit_stamp` (`app/services/sync.py:60`), used by
  the sync and by `adhoc._fetch_live`/`_live_activity` (`adhoc.py:190,216`). No migration:
  the column already meant the committer date and its name is git's own word for it.
- **A closed pull request had no closure date.** `pull_requests` stored `merged_at` and
  nothing else, so a pull request closed without being merged carried no date at all, and
  the payload sent an explicit null to stop the model reading the open date as the closure.
  `closed_at` is now a column, populated in the sync and sent by both report paths
  (`app/models/__init__.py:280`, `sync.py:218`, `generation.py:43`, `adhoc.py:177`,
  migration `0016_pull_request_closed_at.py`). Existing rows stay null: GitHub sends the
  value on the payload and the sync never read it, so it is nowhere in this database to
  recover, and each row fills in the next time GitHub lists that pull request as updated.
- **A refused first question left an empty conversation behind.** The composer opens a
  conversation for a first question because the API takes a message on a conversation that
  already exists; when the message is refused, the conversation it opened is deleted again
  (`services/pulse/frontend/pages/chat.vue:308-330`). One conversation pressed into
  existence with the New button is left alone: that is somebody deliberately keeping an empty
  thread. The `discarded` flag exists so the watcher on `conversationId` does not read the
  id returning to null as somebody switching threads and wipe the refusal off the screen
  (`chat.vue:463`).
- **Next week's goals were invented.** The prompt asked for "a short, plausible set of next
  steps implied by the in-progress work", which is the model guessing forward from commits
  and the report presenting the guess as a person's plan. Goals now come from two things
  somebody wrote down: that person's journal entries for the repo during the report's week,
  and the open issues assigned to them, with a milestone due date where one is set. Both are
  in a `stated_intent` block kept apart from the activity (`generation.py:57-104`), and the
  prompt forbids reading goals out of commits, pull requests or reviews, and requires the
  model to say nothing was recorded rather than fill the field (`prompts.py:33-44`).
  The sync was not storing an assignee at all, so `issues` gained
  `assignee_user_id`, `assignee_github_login`, `milestone_title` and `milestone_due_on`
  (migration `0017_issue_assignee_milestone.py`, `sync.py:243-251`).

## Decisions, and the reasoning that is hard to reconstruct later

- **The provider router falls back; it does not require Anthropic.** `ai_provider.active_provider`
  returns Anthropic when the server has an Anthropic key and OpenAI when it only has that
  one (`app/services/ai_provider.py:46-62`). The alternative, requiring Anthropic for the
  surfaces written against it, put the service in a state it was actually in: a deployment
  holding a working OpenAI key answering 502 on every Anthropic surface. A pinned provider
  is still pinned, though. `AI_PROVIDER=anthropic` with no Anthropic key reports nothing
  rather than quietly answering on OpenAI, because pinning is usually about where the money
  goes or what the answers may be trained on, and silently switching would defeat both.
- **The HNSW index does not serve the query it was built for, and that is the correct
  outcome.** Measured on PG16 with pgvector 0.8 at 3000 chunks: an unfiltered
  `ORDER BY embedding <=> $1 LIMIT k` does use the index, but retrieval always filters to
  one repository, and with `WHERE indexed_repo_id = $1` the planner prefers the btree on
  that column plus a top-N sort. The repository filter is what rules HNSW out. The result is
  an exact nearest-neighbour search inside one repository, which is more accurate than an
  approximate one and was 27 ms at that size (`app/services/repo_index.py:544-556`,
  migration `0008_repo_index.py:10-17`). The index is kept because it was built at zero rows
  and cost nothing, and because rebuilding one over a populated table is the expensive case:
  it wants a large `maintenance_work_mem`, which has to be set on a direct connection, and
  Neon's pooled endpoint is PgBouncer in transaction mode and cannot run SET at all. If one
  repository ever grows past this, the fix is a per-repo partial index or a two-step query,
  not a change to the current one.
- **Department ids are stored when an index is enqueued, not fetched from identity later.**
  A Celery task is handed an `indexed_repos` id and nothing else. Department membership
  lives in identity and only a token carries it, so the worker could not see a department's
  API key or its allowance and quietly used the platform's instead: background indexing
  stopped earlier than interactive chat did for the same person, which reads as a bug. The
  alternative was asking identity at run time, which needs a new internal endpoint, a new
  scope, that scope granted to Pulse's service client row in every environment, and it
  degrades back to exactly the behaviour being fixed whenever identity is unreachable.
  Writing the ids at request time has no failure mode and makes the job reproducible: it is
  evaluated against the permissions the requester held when they asked
  (migration `0015_indexed_repo_owner_dept_ids.py`).
- **A user may only raise a cap on spend they are paying for.** Lowering an allowance is
  always allowed. Raising one is refused unless the person or department funding the calls
  is the one being raised: a department qualifies when it has installed a key, a user
  qualifies only when their own key is what resolution picks, because a department key
  sitting above them is the department's money
  (`credentials.py:306-343`). A platform admin raising anything is spending the platform key,
  which is theirs. The refusal says so in those terms and names the way out: add a key and
  the ceiling is yours to set.
- **Citations prove retrieval, not truth.** A validated citation means this repository, this
  file and these lines were really retrieved and really put in front of the model. It does
  not mean the sentence attached to it is correct. That is why an invented source produces no
  citation rather than an unchecked one, and why citations are narrowed to the files the
  answer names: twelve sources on a short answer is more than anyone checks, and an
  unchecked citation is indistinguishable from a wrong one (`chat.py:181-192`). The feature
  the product sells is that an answer can be checked, so the honest claim is "here is where
  to look", not "this is right".

## Bugs that only degraded conditions found

- **A provider's per-minute limit read as an outage.** A user indexed several repositories
  and one came back as "the embedding service is unavailable". What OpenAI actually said was
  a 429 naming a 2.768 second wait. The retry was one flat second, so a three second pause
  threw the run away. `provider_limits.call_with_retry` now reads the wait the provider
  states, sleeps through short ones, and gives up only when the wait is longer than a worker
  should be held, raising `ProviderRateLimited`, which callers can tell apart from a real
  outage because the right answer to it is to resume rather than to start again
  (`app/services/provider_limits.py:1-19`). The lesson: an error message that generalises
  what the provider said throws away the one number that made it recoverable.
- **A report dated an issue's opening as its closure.** A real report said issue #6093 "was
  closed on July 13" when July 13 was the day it was opened. The model had `state: "closed"`
  and one date, so it used the date it had. The payload now sends every date a closed item
  could have and sends an explicit null when it does not hold one, so absence is visible
  instead of inferred (`adhoc.py:169-174`). That null is what made the missing
  `pull_requests.closed_at` visible as a real gap rather than an oddity.
- **Best-effort degradation and a missing credential look identical from the outside.**
  Recorded in session 08 and worth repeating here, because the same shape recurred: a
  background job silently using the platform's key instead of a department's produced no
  error, only a lower ceiling than the same person got interactively.

- **All seven suites green:** Pulse backend **1116** (98% line coverage), identity **517**
  (98%), Forge **76** (96%), `packages/ui` **239**, Pulse front end **227**, identity front

  28 new tests written for the three fixes and the goals change.
- **The Pulse front-end build is exercised, not assumed:** `docker compose build pulse-web`
  completed and the container was restarted onto the new image before any browser check.
- **Commit dates, against real GitHub data.** Two `pallets/flask` commits, `7203feab` and
  `de8429ff`, are authored 2026-07-14 and committed 2026-08-11. Filtering the same fetched
  payloads both ways: the author date puts them in a 14 July report and out of an August
  one, the committer date does the opposite. The live payload now carries
  `"committed_at": "2026-08-11T19:44:45Z"` for both.
- **Pull request closure, against real GitHub data.** Three real `pallets/flask` pull
  requests were run through `sync._sync_pull_requests` in a rolled-back transaction: #6124
  and #6043 are closed and unmerged and now store `closed_at` where they previously stored
  nothing, #6096 stores both dates. The transaction was rolled back and the local table is
  unchanged at five rows.
- **The empty-conversation fix, in a browser.** Playwright with Chromium against the running
  stack. With a one-token user allowance, a first question with no conversation open
  produced `POST /chat/conversations -> 201`, `POST /chat/conversations/9026/messages -> 429`,
  `DELETE /chat/conversations/9026 -> 204`: the sidebar still read "No conversations yet",
  the question went back in the box, and the refusal stayed on screen with the message
  "This needs about 23 tokens and you have 1 of your 1 daily AI tokens left". The database
  agreed: no row for 9026, and `llm_usage` unchanged, so the refusal cost nothing. Pressing
  New then cleared the refusal, which is the watcher guard treating a real change of
  conversation differently from a discard. With the allowance restored the same question
  created conversation 9028, kept it across a reload, and switching between three
  conversations swapped the thread with no stale error.
- **Goals, against the real API.** Same repository, same week, same commits. With no journal
  entry in that week and no assigned open issue, `next_week_goals` read "No goals were
  recorded for the coming week." With one journal entry and one assigned open issue added,
  it read "write recovery-code tests and move the rate limiter off in-memory storage ... as
  noted in their journal ... also assigned to issue #31 ... due by June 30, 2026". Neither
  version drew on the week's commits, which were about two-factor authentication. The two
  rows used for that check were fabricated for it and were deleted afterwards.
- **The stack, at the end:** `./scripts/dev.sh check` reports all six endpoints answering,
  three APIs on 8001 to 8003 and three front ends on 3000 to 3002.
- **Testing spend:** one chat answer (8,057) and two report generations (2,640 and 2,807),
  13,504 tokens across three `llm_usage` rows. The refused question cost nothing, because
  the cap is checked before the call. No `llm_usage` row was deleted.

## Known limitations

- **`pull_requests.closed_at` is null for every existing row** and fills in only as the sync
  next sees each pull request listed as updated. A pull request closed long ago and never
  touched again stays null forever unless a full re-list is run.
- **The same is true of `issues.assignee_*` and `issues.milestone_*`.** Both were added this
  session and neither can be backfilled from anything in this database.
- **Only the first assignee is stored.** GitHub sends `assignees` as a list; the sync keeps
  `assignee`, which is the first of them (`sync.py:243`). An issue shared between three
  people is one person's stated intent as far as Pulse is concerned.
- **Journal entries are read from the report's own week.** Somebody who writes their plan on
  the Monday after the week has it missed by that week's report.
- **An assigned open issue appears in every week's goals until it closes.** It is not
  date-bounded, on purpose, because queued work is still queued; the effect is repetition
  across consecutive reports.
- **A week with journal entries but no GitHub activity still refuses to generate.**
  `_total_items` counts commits, pull requests, reviews and issues only
  (`generation.py:156`), so stated intent alone is not enough to produce a report.
- **Playwright is not in the repo or in CI.** The browser check above was run from a
  throwaway install outside the tree, so nothing reproduces it automatically.
- **Nothing is deployed.** `DEPLOY.md` is a runbook that has been walked on paper and
  verified locally, not executed.
