## Gap report — FindYourCribb auth vs the CC-Platforms identity bar

Rated against the 7 must-haves in `CLAUDE.md` → "Identity service — what it MUST do".

### 1. Modern slow password hashing — PASS ✅
`Utils/security.py:23-27` uses `bcrypt.hashpw` / `bcrypt.checkpw` directly (passlib removed per the Housing claude.md — bcrypt >= 4.1 incompatibility). Meets the bar. `validate_password` also enforces 8+ chars, upper/lower/number/special.
- **Reuse:** yes, as-is.

### 2. Short-lived access tokens with id/role claims — PARTIAL ⚠️
`create_access_token` at `security.py:70-74` uses `settings.ACCESS_TOKEN_EXPIRE_MINUTES` (env-driven, value unverified — need to confirm it's 10–15 min, not 60+). Tokens carry `user_id`, `role`, `tv` (token version), and for landlords a `verified` claim.
- **Missing for CC:** no `org_id` or `team_id` claim. CC needs both, because permission checks in Pulse/ML platform run off the token without a DB roundtrip.
- **Reuse:** shape yes, must add `org_id` / `team_id` claims; confirm expiry env default is short.

### 3. Rotatable + revocable refresh tokens — PASS ✅ (above bar)
`security.py:290-408` implements exactly what the bar asks for, and then some:
- Refresh tokens stored as **SHA-256 hashes** at rest, never raw — good.
- **Token families** (`family_id`) with **stolen-token detection**: presenting a revoked token nukes the whole family, killing every session from that login.
- **Access-token invalidation via `tv` (token_version)** — bump on user side and every outstanding access token is dead on next check. This is how "log out everywhere" works before the access token naturally expires.
- `revoke_refresh_token` (single logout), `revoke_all_refresh_tokens` (logout-all / password change).
- **Reuse:** yes, whole module — this is the strongest asset in the codebase.

### 4. Public-key token verification, private signing key inside identity — FAIL ❌
This is the biggest gap. `security.py` uses `jwt.encode(..., settings.JWT_SECRET, algorithm=settings.JWT_ALGORITHM)`. Single symmetric secret → HS256 in practice. Every service that verifies tokens needs the same `JWT_SECRET`, which is exactly what CC rule 4 forbids ("never share the token-signing key with any product").
- **Fix required:** switch to **RS256** (or ES256): identity holds the private key, publishes a **JWKS endpoint** (`/.well-known/jwks.json`) with the public key, products verify locally using the public key. Support key rotation via `kid` header.
- **Reuse:** encode/decode helpers keep their shape, but swap symmetric key → asymmetric key + JWKS.

### 5. Organisations, teams, memberships — FAIL ❌
FindYourCribb has **no org/team/membership model**. It has four separate user-*type* tables (`User`, `Landlord`, `Writer`, `Admin`) representing what a person **is**, not what they belong to.
- **Fix required (net-new):** Org, Team, Membership tables. One `User` → many memberships → each carries a role scoped to a team/org. Products reference these by id only.
- **Reuse:** none. This is fresh work.

### 6. Roles/permissions the products can act on — FAIL ❌
`UserRole` enum is a fixed list of user-types. Manager-vs-engineer (which Pulse's approval flow needs) doesn't exist. `require_role` dependency exists (`security.py:277-288`) but only checks the type-role, not a scoped role.
- **Fix required:** roles live on the membership row, not the user. Role list at minimum: `owner`, `admin`, `manager`, `engineer`. Access token carries the role for the currently-active org/team.
- **Reuse:** the `require_role` factory pattern is reusable — swap what it checks against.

### 7. Boring flows — MOSTLY PASS ✅
- **Expiry:** ✅ handled in `decode_access_token`.
- **Refresh:** ✅ (see #3).
- **Logout / revoke:** ✅ single + logout-all.
- **Password reset:** ✅ `create_password_reset_token` / `decode_password_reset_token` with `purpose` claim and 1hr expiry (`security.py:48-68`). Not tied to the refresh-token blacklist though — password change should also `revoke_all_refresh_tokens` (verify in `Routes/user.py` before shipping).
- **2FA:** not present (bar says "plus, not required now").

### Architectural mismatches beyond the 7 rules
These matter because CC-Platforms is a monorepo of **separate services**, not one FastAPI app:
- **Auth is bundled with product logic in FindYourCribb.** `security.py` imports `User`, `Landlord`, `Writer`, `Admin` tables directly and does DB lookups on every request. For CC, `services/identity/` is its own service; Pulse and the ML platform verify tokens **locally** using the public key and **trust the claims** — no cross-service DB lookups, no import of identity's tables.
- **Four `OAuth2PasswordBearer` schemes → one.** CC has one identity, so one token-issuing endpoint and one bearer scheme.
- **Direct DB access in dependencies (`get_current_*`) has to go away for downstream services.** In identity itself, DB lookups are fine (needed to check `token_version`, account status, etc.). In Pulse / ML platform, the `get_current_user`-equivalent should be pure token verification returning claims, no DB call.

## Decisions made this session

| Access token lifetime | **15 min** | Standard short-token / long-refresh pattern |

| Python version | **3.14** | Same as FindYourCribb prod; no code-style impact |
| User profile ownership | Identity owns name/email/avatar; each product owns its own product-specific fields keyed by `user_id` | Clean boundary — no product needs identity's permission to add a field |

### Multi-org — plain-terms implication
Build a `memberships` table joining users ↔ orgs from day one, but only ever create one row per user for now. Access token carries a single `org_id` (the "active" one). Cost now: ~30 min extra schema work. Cost if we skip it and multi-org is later required: painful migration + reworking token claims + updating every product's permission check. Recommendation: build it, keep it single-use, flag for supervisor.
